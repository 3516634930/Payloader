## 批次 G：解码引擎共享化拆分（纯重构）

**问题**：编解码工作台全部逻辑（154 个操作的元数据、transform、参数处理、智能解码）集中在 `src/components/EncodingTools.tsx` 一个约 1.95 万行的文件里，无法被其他视图复用。

**需求**：把解码引擎从组件中剥离成可复用的共享模块，为批次 H 的"两个视图共用一个引擎"做准备。行为零变化。

**方向**：
- 引擎层（操作元数据数组、OperationId/Category 类型、transform 实现、参数解析、智能解码评分逻辑）迁到 `src/utils/codec/` 下的模块，按现有分类或技术域分文件，避免再造一个万行文件。
- `EncodingTools.tsx` 只留视图层（布局、状态、交互），从共享模块导入。
- 不改任何操作的行为、名称、参数、评分逻辑；`npm run verify:codec` 与 `scripts/verify-encoding-tools.mjs` 回归必须零差异。

**预期效果**：`EncodingTools.tsx` 显著瘦身（目标 5000 行以内）；共享模块可被任意视图按"操作 id 子集"消费；全部门禁与批次 A-F 验收项零回归。

**验收**：verify:codec / test / typecheck / lint 全绿；gap-test 结果与重构前完全一致（42/47，有效分 42/42）；编解码 UI 手测无任何变化。

## 批次 H：第三个 Tab「CTF 解题」+ 操作受众分流

**问题**：编解码工作台混装"渗透 payload 处理"与"CTF 解题"两类场景。渗透用户翻工具时被 CTF 杂项干扰，CTF 用户解题时又被工程向操作淹没，不符合两个真实场景的使用习惯。

**需求**：顶部导航新增第三个 tab「CTF 解题」（载荷 / 工具命令旁边），切换到独立的 CTF 解题工具箱视图；编解码 tab 瘦身为真实渗透场景的操作集合。两个视图共用批次 G 的引擎，同一操作不在两个视图重复实现。

**方向**：
- `ActiveTab` 联合类型增加 `'ctf'`，Header 的 tab 切换器支持三态，移动端模块选择器同步。
- 给操作元数据加受众标记：`ctf`（解题专属）、`pentest`（渗透专属）、`both`（两边都显示）。编解码视图渲染 `pentest + both`，CTF 视图渲染 `ctf + both`。
- 分流原则与参考清单（允许按语义微调归类，但改动需在交付说明中列出）：
  - **移入 CTF（标 `ctf`）**：全部古典密码（vigenere / beaufort / autokey / atbash / bacon / polybius / tap-code / playfair / hill2 / substitution / affine / rail-fence / scytale / columnar / porta / gronsfeld / bifid / trifid / four-square / nihilist / adfgx / adfgvx / enigma / frequency-analysis）；ROT/XOR 破译（rot-bruteforce / rot8000 / xor-bruteforce / xor-known-plaintext / magic-xor-helper）；解题杂项文本（brainfuck / ook / keyboard-shift / reverse-text / zero-width）；冷门与取证编码（z-base-32 / base45 / base91 / base32768 / bech32 / base58check / xxencode / uuencode / yenc / bubble-babble / a1z26 / morse / nato-phonetic / baudot / bcd / gray-code / dna-code / gsm7 / sms-pdu）；现代密码攻击助手（rsa-raw / rabin-raw / rsa-helper / coppersmith / discrete-log-helper / mt19937-helper / lcg-helper / lfsr-helper / hash-length-extension-helper / crypto-attack-helper / bip39-seed / pgp-parse / cbc-padding-demo）；smart-decode。
  - **两边共享（标 `both`）**：base64 / base64url / base32 / base36 / base62 / base58 / hex / binary / octal-codes / ascii-codes / ascii85 / url-component / url-form / unicode-escape / js-string / html-entity / xml-entity / utf7 / c-string / json-string / unix-time / quoted-printable / utf16-bytes / gzip / deflate / data-url / xor / rot。
  - **渗透专属（标 `pentest`）**：其余全部，包括 JWT 族、哈希与 HMAC、hash-identify、AES/DES/RC4/ChaCha 全系、OpenSSL 格式、JSFuck/aaencode/jjencode（payload 混淆绕过手法）、CBOR/MessagePack/Protobuf/BSON（真实协议解析）、PEM/ASN.1/JWK/SSH、Punycode、Basic Auth/Query String、Fernet/HOTP/TOTP。
- CTF 解题视图的信息架构按解题流程组织：智能识别（smart-decode 置顶大输入框）→ 古典密码 → 现代密码攻击 → 编码与取证杂项；沿用批次 A 的候选评分展示与导航分组二级菜单规则。
- smart-decode 已有的 flag 格式识别内部逻辑，在解码结果区以徽标显式展示识别到的 flag 格式（只做展示，不做新算法）。
- 编解码 tab 瘦身后若某分类被搬空则移除该空分类。

**预期效果**：渗透用户打开编解码只看到真实工作会碰到的操作；CTF 用户切到解题 tab，从智能识别到古典/现代密码按流程走完解题链路；两边共用引擎与实现，无重复代码；三 tab 在桌面与移动端均布局正常。

**验收**：分流后两视图操作数之和 = both + ctf + pentest 总数无遗漏；CTF 视图粘贴一段 Base32 flag 一步解出并显示徽标；编解码视图粘贴 URL 编码 payload 正常解码；verify:codec / test / gap-test 零回归；移动端三 tab 不溢出、抽屉导航正常。

## 批次 I：收尾验证与体验走查

**问题**：批次 G/H 属于结构性改动，需要一次独立于实现者的整体验证，防止"门禁过了但用户体验坏了"。

**需求**：站在两类真实用户视角做端到端走查，修复走查中发现的 P0/P1 问题。

**方向**：
- 浏览器真实运行走查三条用户旅程：①渗透用户——载荷 tab 查 payload → 编解码 tab 编码/解码 payload → 工具命令 tab 查命令；②CTF 用户——解题 tab 智能解码 → 古典密码解题 → 现代密码攻击辅助 → 编码杂项；③新用户首次进入，三个 tab 语义是否一看就懂。
- 防呆测试：三 tab 快速连点切换、输入超长文本、空输入解码、刷新后 tab 状态、390px 移动端、键盘可达与焦点。
- 检查 console 无报错、i18n 双语完整、亮暗主题一致。
- 发现的问题按 P0/P1/P2 处置：P0/P1 修复，P2 记入交付说明。

**预期效果**：两条用户旅程全程无阻塞；发现缺陷全部处置并有记录；交付说明含走查证据（截图或步骤描述）与 P2 记账。

**验收**：全部门禁复跑全绿；走查问题清单完整（含处置结论）；批次 H 的验收项在走查中逐条复验通过。
