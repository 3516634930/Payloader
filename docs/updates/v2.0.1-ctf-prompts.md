# Payloader v2.0.1 CTF 解题能力增强：开发提示词

> **生成日期**：2026-09-20。基于 47 用例真实矩阵实测（脚本：`output/ctf-gap-test/gap-test.mjs` 与 `op-check.mjs`，node 直接运行可复现）。
> **使用方式**：一个批次一个新会话，把提示词整段发给 AI。批次 A 必须最先做。怎么做由 AI 自主决定，但每个批次的验收标准必须满足。

---

## 实测结论（供参考，不用发给写代码的 AI）

- **A 类·系统性缺陷**：Base32/36、Binary、Octal、A1Z26、Reverse、ROT47、QP、XOR 单字节共 9 类题型在智能解码下全部失败。根因是同一个：智能链选候选靠"第一个非空"而不是"解码质量最优"，被 Base64/Base91/mod37 这类宽编码抢占。各解码器单独调用全对，纯排序问题。
- **B 类·操作不存在**：xxencode、z-base-32、base32768、JSFuck 还原、aaencode、jjencode、NTLM 计算、bcrypt/argon2、PGP 解析、RSA-OAEP、Coppersmith、padding oracle，共 14 项。
- **C 类·古典密码无密钥破译缺失**：Playfair/Bifid/Trifid/ADFGX(V)/列换位等带密钥能用，无密钥不会自动破。
- **D 类·小缺陷**：两处 GBK 乱码正则。

## 批次 A：智能解码候选排序修复（最高优先级）

```text
你负责修复 Payloader 的智能多层解码器。工作目录：D:\项目\payloader，核心文件 src/components/EncodingTools.tsx（15112 行）里的 smartDecode 函数。

问题：目前智能解码选候选的方式是"每层取第一个解码非空的结果就采纳"。实测导致 Base32/Base36、二进制、八进制、A1Z26、Reverse、ROT47、Quoted-Printable、XOR 单字节这 9 类题型全部失败——密文被更宽松的编码（Base64/Base91/mod37 数字解码）抢先解出乱码并采纳。注意：各个解码器本身都是正确的（单独调用没问题），坏的只是候选排序。

需求：改成"解码结果按质量评分、取最优"。质量维度你自己设计，方向上应包括：可读文本占比、英文相似度、CTF flag 模式加成、解码结果与原输入的区分度。另外 hex/字节流解码出非文本时，应继续尝试现有的 XOR 智能暴力逻辑。

约束：不要改任何单个解码器的算法，只动候选选择；保持现有输出格式兼容；智能解码单次调用性能不能明显劣化。

预期效果：用户拿到上述 9 类题型的密文，直接粘贴进智能解码就能一步出明文，不再出现"被 Base64 解成乱码还自以为解出来了"的误导结果；智能解码的输出从此可信——它给出的答案就是它当前找到的最优答案。

验收：
1. node output/ctf-gap-test/gap-test.mjs 运行，编码组与现代组基本全过（该脚本已包含这 9 类题型的真实样本）。
2. npm run verify:codec（现有 114 个回归）全绿；npm test、npm run typecheck、npm run lint 全绿。
3. 在 scripts/verify-encoding-tools.mjs 里为这 9 类题型补上智能解码路径的回归用例。
```

## 批次 B：新增编码操作

```text
你负责给 Payloader 编码工作台新增操作。工作目录：D:\项目\payloader，核心文件 src/components/EncodingTools.tsx（新操作按文件里现有的操作注册模式接入即可，回归测试写在 scripts/verify-encoding-tools.mjs）。

需求：新增以下操作，让这些 CTF 常见题型能被直接解码：
1. xxencode——与现有 UUencode 同构，换字母表。
2. z-base-32——小写无 padding 的 5 位分组编码。
3. NTLM 哈希计算——并入现有 hash 操作（内部就是 md4(hex(utf16le(密码)))，md4 实现已存在）。
4. base32768——Unicode 高密度编码。

算法参考：gchq/CyberChef（github.com/gchq/CyberChef，Apache-2.0）的 operations 源码、qntm/base32768（MIT）。

预期效果：遇到 UUencode 变体、z-base-32、base32768 这类"稍冷门但一眼像 Base 系列"的密文时，不再需要去外部工具解码；拿到 NTLM 哈希可以直接在平台算出验证值，编码覆盖面追平主流 CTF 工具箱的日常所需。

验收：
1. 每个新操作在 verify-encoding-tools.mjs 有往返或标准样例回归。
2. npm run verify:codec、npm test、npm run typecheck、npm run lint 全绿。
```

## 批次 C：混淆代码还原（JSFuck / aaencode / jjencode）

```text
你负责给 Payloader 增加混淆 JS 还原能力。工作目录：D:\项目\payloader，核心文件 src/components/EncodingTools.tsx（现有 jsfuck 相关逻辑只做识别提示，不做还原）。

需求：新增三个解码操作，把 JSFuck、aaencode、jjencode 混淆代码还原为可读 JS 源码。

方向：这类混淆本质是构造字符串再执行，还原 = 自写小型求值器把表达式算出字符串，而不是真的执行。安全底线：严禁 eval/new Function/任何真实执行；必须有步数和输出长度上限防挂死。

预期效果：Misc 题里最常见的三类"看得懂是 JS 但全是符号/颜文字"的题，粘贴进平台就能直接还原出可读源码和隐藏的 flag，不用再去 CyberChef 或在线工具中转；且还原过程是纯静态求值，恶意输入在平台内不可能被执行。

验收：
1. 三个操作各有回归用例（含经典 alert(1) 样本与 flag{...} 样本的往返），畸形/超长输入安全返回错误。
2. npm run verify:codec、npm test、npm run typecheck、npm run lint 全绿。
```

```text

需求：为 Playfair、Bifid、Trifid、ADFGX、ADFGVX、列换位 6 种密码增加无密钥时的自动破译，接入现有智能解码的无命中回退链。方向：密钥扰动 + 英文评分的爬山/模拟退火，长文本统计可解、短文本允许失败；控制整体耗时（单个样本秒级、不能卡死界面）。

预期效果：比赛里拿到一段 Playfair/ADFGVX 密文而题目没给密钥时——这是这几种密码最常出的形态——直接粘贴智能解码就能自动破出明文；平台从"带工具手册"变成"自带破译器"，古典密码题基本不用出站。

验收：
1. 每种密码有智能解码路径的回归用例（用带密钥操作生成密文、足够长的英文明文，断言无密钥还原）。
2. npm run verify:codec、npm test、npm run typecheck、npm run lint 全绿。
```

## 批次 E：现代密码增强

