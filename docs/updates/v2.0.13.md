# Payloader v2.0.13 更新计划：升级路径指引

> 策略说明：本版原为"企业级高并发读取、横向扩容与灾难恢复"。2026-09-20 双仓库策略确认后，多节点/HA/灾备的**工程实现移交部署版仓库**（Payloader-Enterprise v0.4 里程碑，见 [deployment-repo-plan.md](deployment-repo-plan.md)）。Node 主线本版号重新定义为：让社区用户清楚"什么时候该换部署版、怎么迁"。

## 目标

企业级规模能力（多节点、高可用、大容量、灾备）由部署版承载；本版在 Node 社区版交付的是清晰的升级路径：官方托管扩容方案 + 自托管用户迁移指引。

## 需求背景

社区版的价值是"零环境解压即用"，把它推向多节点企业架构会同时伤害两个用户群：自托管用户背上不需要的复杂度，企业用户也得不到真正的 HA。双仓库分工后，两类需求各有归宿，剩下的问题是——已经跟着社区版长大的用户，规模变大后该怎么办？答案必须写清楚，不能让用户自己撞墙。

## 新增/变更功能

- 官方在线服务扩容方案：官方站点的规模增长由部署版（Java）承载，切换方案、数据迁移与回滚预案成文。
- 自托管扩容指引进文档：按规模分档给出建议——小规模留在社区版（SQLite 单机足以覆盖的区间）、规模增长后迁移到部署版，判据写明（并发量、内容量、可用性要求）。
- 社区版 → 部署版迁移路径：依赖 v2.0.12 的数据互通格式，提供"导出 → 导入 → 校验"三步迁移工具与演练文档。
- 容量与边界说明：社区版文档明确单机形态的合理容量区间与性能预期，不承诺也不暗示企业级 SLA。

## 预期效果

- 社区版用户从第一天就知道成长路径：小用 SQLite 单机，大了迁部署版，数据带得走。
- 没有人会把社区版硬撑成企业架构——那条路的答案在另一个仓库里，且有现成的迁移工具。
- 官方在线服务的规模化与社区版的简单性互不拖累。
